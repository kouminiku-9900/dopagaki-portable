# 実機テストの手順（持ち出し1回分）

PSPを持ち出す回数を減らすため、実機でしか確かめられないことを1回の持ち出しにまとめて確認します。実機で起動するものは、起動したら自動でテストを最後まで実行し、結果をメモリースティックに保存します。ボタン操作や画面の書き写しは要りません。

## 今回（持ち出し1回目）：段階0のメモリ調査＋HANDOFFの未確認項目

所要時間はPSP側で10分ほどです。

### Macでの準備（PSPを接続して）

```sh
./scripts/build_memprobe.sh   # 調査用EBOOTを3種類作る（数秒）
./scripts/build.sh            # 最新のkomi-tube（既にPSPに入っていれば不要）
./scripts/field_sync.sh install
```

`install` は `KOMI_PROBE_M0` / `M1` / `M2` とkomi-tubeをメモリースティックへコピーし、コピー後に内容を照合します。komi-tubeの `data/`（設定）は上書きしません。

### PSPでの作業

1. **komi-tube memprobe (m2)** を起動する。10秒ほどで `Done.` と表示されるので、×で終了する。
2. 同じように **(m1)**、**(m0)** も起動する。
3. **komi-tube** を起動し、「検索 → 再生 → 関連動画 → 再生」を2〜3周繰り返す。失敗してもそのまま続ける（エラーは自動で記録されます）。

調査用EBOOTは起動するだけで、Wi-Fiには接続しません。`ME test: high memory` の表示で30秒以上止まった場合は、POWERを長押しして電源を切ってください。そこまでの結果は保存済みで、止まったこと自体が「MEは高位メモリを読めない」という結果になります。

### Macでの回収

```sh
./scripts/field_sync.sh collect
```

`field-logs/<日時>/` にログを集め、メモリースティック上のログを `*.<日時>.old.txt` に改名します（次回と混ざらないように）。調査結果の表は `memprobe-report.md` に出力されます。通信ログには期限付きの動画URLが含まれることがあるため、`field-logs/` はGitに入れていません。

## 調査EBOOTが確かめること

| 項目 | 方法 | ログの行 |
|---|---|---|
| MEMSIZE設定（0/1/2）ごとのユーザー領域の大きさ | 3種類のEBOOTでそれぞれ計測 | `mem` / `map` |
| 空き領域が`0x0A000000`の上下どちらにあるか | 最大の空きブロックを順に確保して地図を作る | `map` / `map-total` |
| AVモジュール（avcodec, mpeg_vsh）とネットワークの初期化で減るメモリ | 読み込みの前後で空き容量を比較 | `module` / `net` / `mem` |
| ME専用6MBを`0x0A000000`未満の4MB境界に置けるか | 4MB境界ごとに確保を試す | `me-candidate` / `me-region` |
| 残りを汎用アリーナにしたときの大きさ | 最上位から確保 | `arena` |
| MEが読めるメモリ範囲 | 同じAACフレームを、低位・揮発メモリ・高位にバッファを置いてデコードし、出力が一致するか比較 | `codec-result` |
| 開いて閉じるのを10回繰り返したときの漏れ | 低位でデコーダーの初期化とデコードを10回 | `cycles` |

MEの試験は、止まっても他の結果が残るように「低位 → 10回繰り返し → 揮発メモリ → 高位」の順で行います。ログは1行ごとに保存します。

PPSSPP（headless、v1.20.4）では3種類とも最後まで完走することを確認済みです（MEMSIZE=1で約54.6MB、0と2では約22.6MB。PPSSPPはMEの制約を再現しないため、高位のデコードも成功します）。実機の値はこれとは異なる見込みです。

## 結果から決めること

- **MEMSIZE**：実機でm1とm2のどちらが拡張メモリを得られるか。今のkomi-tubeのランチャーはm2（CMakeの既定値）です。
- **ME専用領域の位置**：`me-region`のアドレスを段階1の`media/Player`の固定値にする。本番のEBOOTはプログラムが大きいので、4MB境界の候補が1つ上にずれる前提で余裕を見ます。
- **アリーナの大きさ**：`after-modules`の空きから、ME領域と予備1MBを引いた値。リングバッファ8〜12MBと、画面・通信用の割り当てをここから決めます。
- **MEが読める範囲**：`mixed-io-high`が失敗なら、入出力バッファも低位に置く必要がある（リングバッファから低位のステージングへコピーする設計にする）。`volatile`が成功なら、揮発メモリ（4MB）もME用に使える候補になります。

## 持ち出しの予定（全体）

実機でしか確認できないのは、主にデコード、ME、実機のメモリです。それ以外はMac上の実通信テストとPPSSPPで先に確認し、実機はまとめて確認します。

| 回 | 時期 | 実機で確認すること |
|---|---|---|
| 1 | 今回 | メモリ調査（3種類）、既存版の「検索→再生→関連→再生」 |
| 2 | 段階1の完成時 | ブラウザなしEBOOTで10本連続再生（起動するとテスト用の動画IDリストを自動で順に再生し、ログを残す）。段階2のHTTP自前化もこの時点で間に合えば一緒に確認 |
| 3 | 段階3の完成時 | ネイティブ画面の操作（検索→結果→再生）、スリープ復帰 |

段階4（機能を戻す）と段階5（撤去）は、必要に応じて3回目にまとめるか、使いながら確認します。
